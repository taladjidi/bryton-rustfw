# The Rider S810: a plan

How this firmware could also run on Bryton's Rider S810, what differs from the S510, and in which order to do it.
No S810 unit has been seen yet (2026-10-26): every fact below comes from Bryton's own S810 files, read for
interoperability (OS R049, bootloader R002 of the S810, from Bryton's update server like `tools/fetch_firmware.py`
does for the S510), or from published specs. As in BOARD.md, **inferred** means deduced and not traced, and
**to see** means only a unit can tell. Function addresses are those of the S810 R049 image (code at 0x08......)
or of the S810 bootloader (0x0801....).

The short version: the platform is the same (STM32H747, 64 MB SDRAM, eMMC, the same Nordic image, the same sensor
and GNSS drivers), but three things are not "only the screen":

1. **The panel is on MIPI DSI**, not SPI: a new transport, a DSI host and its PLL to bring up.
2. **The S810 runs its code from the MCU's internal flash** (0x08020000), not from SDRAM. The bootloader programs
   that flash during an update, and does not copy anything to SDRAM at boot.
3. **The pins moved:** the S810's MCU uses ports J and K, so keys, the USB line and most control pins differ.

What stays the same (in the stock code, about 94 to 100 % of the device logic is shared between R039 and R049:
sensors, workouts, routes, settings, file system, ride, log, GPS): the volume layout (`\Activities`, `\System`,
`\Workout`, `\PlanTrip`, `\Map`), the FIT files, the INI files, so `src/storage/` needs nothing new. To check on a
unit: the volume's size and `\System\device.txt` (`Model=RiderS810`).

## 2. Stock firmware and bootloader: what differs

**The update file.** `IMG.bin` is the S510 format (gzip, or raw when 0x94 holds `R` + 3 digits; larger than 1 MB,
smaller than 10 MB; the last 4 bytes the additive sum of the others), **plus one check:** the 16 bytes before
the end of a file named `IMG.bin` must start with `RiderS810` and a zero (R049's own `img.bin` ends with
`RiderS810\0\0\0` then the sum). Without it the sum is forced wrong and the file is refused (0x080a4b76). The tag
at 0x94 is `R049`, the size word at 0x98 is the image size, as on the S510. Battery at least 38 %.

**How an update lands (0x080a3908 and bootloader 0x080187dc, 0x08018ca8):**
1. The OS writes the image to an eMMC staging area (2 sectors past its base), reads it back and checks the sum.
2. It sets RTC backup register 13 = 2 (staging offset), 14 = the size in sectors, **15 = 0x5547** ("UG"), and
   restarts.
3. The bootloader reads register 15 at every start. On 0x5547 (or 0x5231..0x5233, its retries) it copies the
   first 0x1e0000 bytes of the staged image to **internal flash 0x08020000** (erasing each 128 KB sector when a
   write starts at its first byte) and the rest to the eMMC OS area, compares both with the staging area, then
   writes 15 = 0x4649 ("FI"). On a mismatch it tries again (R1, R2, R3) and then gives up (15 = 0).
4. Then it checks the keys, and otherwise sets MSP from 0x08020000 and jumps to the reset vector at 0x08020004.
   It never copies to SDRAM: the OS fetches its own tail (inferred: its SDRAM code runs after the FMC set-up).

So **register 15 must never hold 0x5547 or 0x5231..0x5233** from this firmware, or the next start reflashes from
whatever is in staging. This firmware does not use 15 today (settings.rs); it does use 13's neighbour 14 (the
shifting system), which the bootloader reads only in update mode.

**Engineer Mode (bootloader USB mode).** Same "BRYTON MASS STORAGE" device and the same vendor sub-commands as on
the S510 (0x0c write 2 KB, 0x0d read 2 KB, 0x04 sum of the bootloader, 0x14 clear all 32 backup registers), but
the offset is split: **below 0x1e0000 it is internal flash** (0x08020000 + offset), at or above it the eMMC OS area
(offset - 0x1e0000). So `iaprecover.py --write` of a whole image puts each part where the update would.
Differences that matter:
- A flash sector is erased only when a write starts at its first byte. Re-writing one 2 KB chunk in the middle of a
  sector programs over written flash: the bootloader then loops forever on "program flash error" (a four-button
  restart is the way out, inferred). A retry must restart at the sector's start.
- An erase or program error also loops forever (same way out).
- Entry: the bootloader reads PK3 (Page, inferred) and PJ8, and enters USB mode when neither reads 1. Which keys to
  hold, and whether the cable must be in, is **to see** (S510: Page held with the cable in). With no USB activity
  for 5 s it starts the OS.
- Sub-command 0x0b (read internal flash) is in its table; whether the USB read path reaches it (it does not on the
  S510) is to see.
- The bootloader itself (0x08000000..0x0801ffff) is never inside the writable range (offset < 0x1e0000 from
  0x08020000), so neither path can overwrite it.

**The Nordic image** is byte-identical to the S510's: `src/drivers/nrf.rs` and `ble.rs` need nothing.

## 3. The diagnostics tool (phase 0)

Something to give an S810 owner before any unit is here: `tools/s810_probe.py`, plain Python 3, no dependency
for part 1. It never writes to the unit and never flashes anything. Its output is one zip with `manifest.json`
(the tool's version, what was collected, what never is, the filter patterns, a SHA-256 per member), which the owner
opens and reads before sending it. Nothing personal goes in it: no rides, no positions, no names, no file names
outside `\System` (ride files are named by date and time), no INI values, no UUID.

**Part 1, the stock USB drive (built, `drive`; `selftest` in check.sh on a made-up volume).** The unit runs stock
and is plugged in; the drive is mounted as for any sync. The tool opens files for reading only. It takes:

| item | tells us | for phase |
|---|---|---|
| `\System\device.txt`, UUID line removed | OS, bootloader, Nordic and language versions, model (`Model=RiderS810`): which R0xx the plan must match | 4, 5 |
| `\System` file names and sizes; INI section and key names, values replaced by `<v>` | whether stock's settings files are the S510's (rustfw imports them, `src/storage/ini.rs`) | 9 |
| per top-level folder: file count, total size, extensions | the volume layout is the S510's (`src/storage/`) | 9 |
| `\Debug\*.log`, only the lines matching hardware patterns (panel type `LCD Type ...`, `touch ic resolution`, `[Barometer] model`, `Light sensor cali`, `Image version ... IAP ... Nordic`, Nordic SoftDevice version, `SC89620` registers, reset causes, faults), after dropping any line with a position, a name, an address or a long decimal | the panel variant (one of three), the touch chip's resolution, which barometer, the charger's set-up, the Nordic stack, crashes | 1, 6, 7, 8, 9 |
| volume size and free space | the eMMC size (the OS area sits at its end) | 3, 5 |

The debug log is written only after an abnormal restart (stock keeps its log in RAM through a warm reset; seen on
the S510: a four-button restart, cable out, then the next start saves `\Debug\<date><time>.log`). So the owner's
steps: switch on unplugged, wait for the main screen (a minute outdoors so the GPS speaks), restart with the four
buttons, wait for the main screen again, plug in, run `tools/s810_probe.py drive`. Whether the S810 saves it the
same way is to see; an empty `debug/` in the zip says it did not.

**Part 2, the bootloader's read commands (designed, `engineer`, later).** Needs libusb (as `iaprecover.py`) and
sudo, and the Engineer Mode key combination of the S810, unknown (section 2). It sends only the vendor
sub-commands that the S810 bootloader's code shows to be reads (0x0801...), from a fixed allow-list; the tool has
no write path at all, and refuses any other sub-command:

| sub-command | what it returns | read-only | for phase |
|---|---|---|---|
| 0x04 | byte sum of the bootloader's 128 KB | sure (a loop over flash) | 5: the bootloader is the one analysed |
| 0x0d | 2 KB of the image: internal flash below 0x1e0000, the eMMC OS area above | sure | 3, 5: the installed image; only its SHA-256 per 128 KB and the differences from R049 are kept, never the image |
| 0x15 | a constant (erase "ready") | sure | none, a link check |
| 0x19 | four constant bytes | sure | none, a link check |
| 0x03 | 2 KB "UUID" block | sure, but an identifier | left out |
| 0x10 | 4 KB of an eMMC area | sure, but unknown content | left out until traced |
| 0x02, 0x0c, 0x0e, 0x0f, 0x11 | writes | no | never |
| 0x14 | **clears all 32 RTC backup registers** | no | never |
| 0x05, 0x0b, 0x13 | not traced / not reachable | unknown | never |

Warning for the owner in the tool's output: in Engineer Mode the computer sees a raw, unformatted disk; macOS or
Windows offers to initialise it: **always Ignore / Cancel**. Leaving the mode is unplugging the cable (the unit
restarts).

**Part 3, what the owner can see without any tool:** Settings > About (versions, a photo of it), and photos of the
board only if the owner opens the unit anyway (never asked for): both sides of the
main board, square to the camera, sharp enough to read chip markings, plus close-ups of the MCU, the panel's flex
connector and its label, the GNSS module, the chips near the USB connector (PHY, charger) and the battery's label.
They name the MCU package, the GNSS module, the touch chip, the PHY and the battery capacity (phases 1, 3, 8, 9).
No photo with a location or a person in it.

No hidden diagnostic menu was found in R049's UI classes (Settings::About is the only information screen); stock
can save screenshots (`%s%02d.bmp`), but what triggers it is not traced.

**Risks:**
- **Internal flash writes.** On the S510 nothing ever writes the MCU's flash; on the S810 every install does (the
  bootloader does it, not this firmware). A power cut while it programs leaves no valid OS in flash; the
  bootloader itself is outside the range and Engineer Mode should still come up (to see before anything else).
- **The bootloader's state at the jump** (clocks, MPU, caches, VOS) is unknown, and the S810 OS sets the SDRAM up
  itself, so the first boot steps are new code with no S510 precedent: `DIAG_STOP` stage by stage.
- **DSI bring-up blind:** no screen until the DSI host, its PLL, the D-PHY and the panel all agree; the dev link
  (USB) should come up first so `peek` can read the DSI status registers.
- **Panel variants:** three init sequences; a unit may carry one not seen yet.
- **Backup register 15** (section 2).
- **Layout:** the letterbox is cheap; a real 282 x 470 layout touches most drawing code, and every redraw box must
  stay minimal (AGENTS.md, Performance first).
- **Two builds to keep green:** `check.sh` time roughly doubles for the test and build stages.

## 5. First steps on a real S810

Never touch the bootloader or the option bytes; every write recorded in bryton-S510-mods' FLASHLOG, as for the S510.

0. **The probe:** `tools/s810_probe.py drive` (section 3) on the unit as it comes, before anything else.
1. **Recovery first.** Find the Engineer Mode key combination; check `iaprecover.py --boot-sum` against the S810
   `iap.bin` (proves the bootloader is the one read here); read back the whole image (flash part and eMMC part) and
   compare it with R049's `IMG.raw`; write R049 back over itself and boot (proves the way back, as on 2026-10-22
   for the S510).
2. **Read the volume:** `\System\device.txt`, the folders, the eMMC size (the drive's size in Finder).
3. **First DIAG build** through Engineer Mode (the update path works too, with the model tail): an image that
   only waits for USB power on PJ8 and resets. Engineer Mode coming back proves code at 0x08020000 ran. Then one
   stage at a time: clocks, SDRAM (write and read back a pattern), USB dev link.
4. **With the dev link up:** `peek` RCC, PWR, MPU, FLASH_ACR and the GPIO ports to compare with Ghidra; `tools/dev.py run`
   for later builds (an SDRAM-linked variant staged by the flash-resident one), so the flash is written only
   when installing.
5. **Then the panel:** DSI host and PLL with `peek` / `poke`, RDID4 read, the variant's init, one filled box.
